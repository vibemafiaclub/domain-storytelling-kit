# 도메인 스토리텔링 워크숍 — VIBE PT 온보딩 과제

> 1회차 수업 전까지 혼자 완주하는 과제입니다. 예상 소요 **4~8시간**. 한 번에 하지 말고 3~4회로 나눠서 하세요.

## 이 과제의 목표

수업에 **만들 것이 확정된 상태로** 오는 것입니다. 구체적으로는 세 가지를 들고 오십니다.

| 산출물 | 내용 |
|---|---|
| `docs/DOMAIN.md` | 현실에서 실제로 벌어지는 일(AS-IS), 거기서 나온 불편함, 그리고 그것이 사라진 모습(TO-BE) |
| `docs/REQUIREMENTS.md` | 이 소프트웨어가 **할 것과 안 할 것**. 안 할 것에는 이유가 붙는다 |
| `docs/USER_STORIES.md` | 마감 순서로 줄 세운 기능 목록. 스토리마다 어느 불편함에서 나왔는지 근거가 붙는다 |

이 세 개가 없으면 1회차에 할 수 있는 게 없습니다. 설계도, 구현도, UI/UX 판단도 전부 "이 업무가 실제로 어떻게 돌아가는가"에서 나오기 때문입니다. 그 재료를 수업 시간에 만들면 12회 중 3~4회를 씁니다. **재료는 혼자 만들어 오고, 수업 시간은 그 재료로 판단을 내리는 데만 씁니다.**

## 준비 (20분)

설치부터 따라 하실 거면 VIBE PT 학생 페이지의 **「VIBE PT 시작하기」**를 보세요. 이 키트를 이미 받으셨다면:

1. 키트를 받습니다 — https://github.com/vibemafiaclub/domain-storytelling-kit 에서 **Use this template → Create a new repository**를 누르고, 이름은 만들 서비스 이름, 공개 범위는 **Private**로 만든 뒤 내 컴퓨터로 clone합니다 (압축 파일로 받으셨다면 압축을 풀고 폴더 이름을 서비스 이름으로 바꿉니다)
2. 이 폴더에서 `claude` 를 실행합니다
3. "templates 폴더의 파일 3개를 docs 폴더에 복사하고, 이 폴더를 내 GitHub 비공개 저장소에 push한 뒤(아직 저장소가 없으면 만들어서) greatSumini 를 collaborator로 초대해줘"라고 말합니다
4. 입력창에 `/domain` 을 쳐서 스킬 5개가 보이는지 확인합니다

Codex 등 다른 도구를 쓰신다면 [`PROMPTS.md`](./PROMPTS.md)를 보세요.

## 대상 고르는 기준

무엇을 만들지 이미 정해두셨다면 그걸로 합니다. 아직 후보가 여럿이면 아래로 고르세요.

- **내가 그 일을 직접 하고 있을 것** — 남에게 물어봐야 답이 나오는 업무면 탈락입니다. 이 워크숍은 내 머릿속을 꺼내는 작업이라, 도메인 전문가가 내가 아니면 시작할 수 없습니다
- **이미 대가를 치르고 있을 것** — 지금 그 일을 엑셀·노션·카톡·수기로 하고 있어서 매일 불편한 업무. "있으면 좋을 것 같은" 서비스는 요구사항이 상상에서 나오므로 탈락입니다
- **등장인물이 2명 이상일 것** — 나 혼자 처음부터 끝까지 하는 일은 불편함이 잘 드러나지 않습니다. 주고받는 상대(고객·거래처·팀원·트레이너 등)가 있어야 합니다

정하기 애매하면 **지금 스프레드시트나 카톡으로 돌리고 있는 업무 중 가장 아픈 것**을 고르세요.

## 진행 순서

각 단계는 **새 세션에서** 시작합니다. 세션 하나가 길어지면 앞의 대화가 뭉개집니다.

### 0단계 · 판 깔기 (30분) — `/domain-scan`

무엇을 다룰지 정하고, 이 업무가 벌어지는 **장면 목록**을 닫습니다. 아직 깊이 안 들어갑니다.

- 산출물: `docs/DOMAIN.md`의 「목적지」와 「장면 목록」
- 끝나는 지점: 장면 5~10개 + 등장인물 전체 + **이 서비스가 걸려 있는 판단**이 한 문장으로 적힘

### 1단계 · AS-IS 인터뷰 (2~3시간, 이 워크숍의 본체) — `/domain-story`

장면 하나씩, 지금 실제로 벌어지는 일을 번호 문장으로 받아 적습니다. 장면마다 무엇이 불편했고 그래서 무슨 일이 생겼는지까지 캡니다.

- 산출물: `DOMAIN.md`의 「AS-IS」 전체 + 「불편함」 표 초안 + 「용어」
- **장면 한두 개 = 한 세션**입니다. 한 번에 다 하려고 하지 마세요
- 답이 안 나오는 지점은 가설로 적고 넘어갑니다. **뒤에서 채워집니다**
- `/domain-story` 는 문서 상태를 보고 다음에 인터뷰할 장면을 스스로 고릅니다. 워크숍이 끝난 뒤에도 현실이 바뀌면 같은 스킬로 고치고, "보여줘"라고 하면 색칠한 문서를 열어 줍니다

### 2단계 · 가르기 (40분) — `/domain-triage`

불편함마다 **해결** / **안 함**을 정합니다. 여기가 이 워크숍에서 **나만 내릴 수 있는 판단**입니다.

- 산출물: 불편함 표의 「가르기」 칸이 전부 채워짐
- 전부 **해결**이 되면 잘못 가른 것입니다. 보통 30~40%는 **안 함**이 됩니다

### 3단계 · TO-BE (1~2시간) — `/domain-tobe`

**해결**로 가른 불편함이 **사라진 모습**을 장면별로 씁니다. 소프트웨어가 끼어드는 단계마다 그 순간의 상황까지 적습니다.

- 산출물: `DOMAIN.md`의 「TO-BE」 전체
- 이 단계 산출물이 그대로 1회차 UI/UX 판단 기준이 됩니다

### 4단계 · 범위 확정 (1시간) — `/domain-scope`

TO-BE를 통으로 따라가 끊기는 곳을 찾고, `REQUIREMENTS.md`와 `USER_STORIES.md`를 만듭니다.

- 산출물: `docs/REQUIREMENTS.md`, `docs/USER_STORIES.md`
- 여기서 **제외 목록**이 나오면 이 과제는 성공입니다

## 완료 판정 체크리스트

1회차에 이게 다 되어 있으면 됩니다.

- [ ] `DOMAIN.md`에 장면 목록이 닫혀 있고, 장면마다 AS-IS가 있다
- [ ] AS-IS가 `[누가] {무엇을} <어떻게 한다>` 번호 문장으로 끝까지 이어진다
- [ ] `/domain-story` 로 문서를 열었을 때 표기 경고가 0개다
- [ ] 반복되는 일마다 「물량·시간」(얼마나 자주·몇 건·한 건에 걸리는 시간)이 있다
- [ ] 판단이 갈리는 곳마다 「사례」가 3건 이상 있다 (실제로 있었던 건, 예외 1건 포함)
- [ ] 내가 직접 하지 않는 일(`— 전해 들음`)은 그 사람에게 확인했거나 「확인할 질문」으로 남아 있다
- [ ] AI 추측에 동의만 한 문장(`— AI 추측`)과 AI가 낸 TO-BE(`제안: AI`)가 표시돼 있다
- [ ] 불편함이 10개 이상이고, 항목마다 **누가 · AS-IS 몇 번 단계 · 그래서 무슨 일이 생기는지 · 증거**가 있다
- [ ] 불편함마다 **해결** / **안 함**과 이유가 붙어 있다
- [ ] **해결** 항목마다 그것이 사라지는 TO-BE 단계가 있고, 서로 번호로 연결돼 있다
- [ ] 소프트웨어가 끼는 TO-BE 단계마다 **그 순간의 상황**(언제·어디서·손이 비었는지·무슨 판단을 하는지)이 적혀 있다
- [ ] 용어 사전에 20개 이상이 있고, 한 대상에 이름이 하나다
- [ ] `REQUIREMENTS.md`에 **제외 목록**이 있고 항목마다 이유가 있다
- [ ] `USER_STORIES.md`의 스토리마다 근거(불편함 번호 · TO-BE 단계)가 붙어 있다
- [ ] "모른다"로 끝나는 문장이 없다 — 답을 얻었거나, **가설 + 무엇을 보면 판정되는지**로 적혀 있다
- [ ] 마지막 내용까지 GitHub 저장소에 푸시되어 있다

## 막히면

카톡 주세요. 특히 **2단계 가르기에서 오래 고민되면 바로 물어보세요.** 여기서 잘못 가르면 뒤 작업이 통째로 방향이 틀어집니다. 나머지 단계는 다소 어긋나도 1회차에 교정 가능합니다.
